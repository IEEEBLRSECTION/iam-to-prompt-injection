The runtime role, written down

runtime-role-policy.json

{
  "Effect": "Allow",
  "Action": "bedrock:ApplyGuardrail",
  "Resource": "arn:aws:bedrock:REGION:ACCOUNT:
    guardrail/GUARDRAIL_ID"
},
{
  "Effect": "Allow",
  "Action": "bedrock:InvokeModel",
  "Resource": "arn:aws:bedrock:REGION::
    foundation-model/MODEL_ID"
}

Allowed

Apply one Guardrail. Invoke one preflighted model. Converse calls use the InvokeModel permission.

Not in this role

Creating or changing Guardrails, IAM changes, other buckets, other models.

Check it

IAM Access Analyzer validates the policy and shows unused access after a test run.

Illustrative · replace REGION, ACCOUNT, GUARDRAIL_ID and MODEL_ID with your preflighted values

Subramanya · 05–17 min

For standalone evaluations, bedrock:ApplyGuardrail is the relevant runtime permission. Model-connected calls need the appropriate inference permissions too. Console listing and setup permissions are separate and belong to the setup identity. If the application needs to read synthetic fixtures from S3 or write logs, add narrowly scoped storage and logging statements, nothing broader. Keep the baseline environment isolated and synthetic: if production-style IAM enforcement requires a Guardrail, use a separately scoped demo baseline rather than weakening that enforced runtime role. Verify the exact actions against current Bedrock IAM documentation before the event.
